# AIHelms 网关与成本管理配置手册（运维向）

本手册面向运维人员，讲清两件事：

1. 平台「网关」是什么、数据怎么流；
2. 在 admin 前端「模型管理」里，如何配置模型的**路由、超时、计费、定价**等高级参数，以及这些参数最终落到了哪里。

阅读完后，你应该能独立完成一个新模型从「建模型 → 建渠道 → 配定价 → 配路由 → 发布 → 验证」的全流程。

---

## 1. 网关是谁

AIHelms **不自己实现模型路由**，网关就是 **LiteLLM**。平台做的事是：

- 在平台数据库里管理「模型 / 渠道 / 凭证 / 路由策略」的**完整配置（超集）**；
- 把这些配置**同步**到 LiteLLM；
- 用户/客户端直接打 LiteLLM 完成推理，LiteLLM 产生 usage、日志；
- 平台**定时拉取** LiteLLM 的 usage/log 落库，做成本和日志分析。

```
admin 配置 → 平台 DB → 同步 → LiteLLM(网关) ← 用户客户端调用
                              ↓
数据分析 ← 平台定时拉取 usage/log
```

关键原则（平台铁律）：**平台 DB 是唯一数据源**。即使 LiteLLM 数据丢了，平台也能恢复。成本报表只读平台落库后的汇总表，**不直接读 LiteLLM 原始 spend**。

### 1.1 地址

| 概念 | 地址 | 来源 |
|------|------|------|
| 网关内部地址 | `http://litellm:4000` | 固定，容器内服务间调用用（`config.py:litellm_url`） |
| 网关对外地址 | `http://<NGINX_SERVER_NAME>:<LITELLM_PORT>` | 由 `NGINX_SERVER_NAME + LITELLM_PORT` 拼接（`config.py:143`） |
| 用户接入示例 | `http://192.168.125.23:4000/v1/chat/completions` | 见 web 端「我的资源」接入指南 |

外部端口由 `LITELLM_PORT` 控制，**容器内部端口 4000 不可改**。

### 1.2 两套调用协议

平台每个模型都有两套接入方式，对应 LiteLLM 里**两个独立 model group**：

| 协议 | 路径 | 鉴权头 | model 字段 |
|------|------|--------|-----------|
| OpenAI | `/v1/chat/completions` | `Authorization: Bearer <key>` | `model_id` 原样 |
| Anthropic | `/v1/messages` | `x-api-key: <key>` + `anthropic-version: 2023-06-01` | `model_id(Anthropic)` |

Anthropic 变体通过**模型名加 `(Anthropic)` 后缀**形成独立路由组（`model_service.py:729`）。同一个底层模型，OpenAI 渠道和 Anthropic 渠道可以分别配置、分别计费、分别路由。

### 1.3 「禁用」是怎么实现的

不删除 LiteLLM 里的记录，而是把 model_name 追加 `__disabled__` 后缀，让它**脱离原路由组**（真禁用，不再被路由命中），同时保留 `litellm_model_id` 不变，历史成本/日志关联完整（`model_service.py:733`）。

触发禁用的两种情况：
- 渠道（deployment）`is_active=false`；
- 渠道关联的凭证 `is_active=false`。

两者都满足才会进入路由池（`_deployment_routable`，`model_service.py:736`）。

## 2. 核心数据对象

运维配置时打交道的是这三层，从上到下：

```
模型 (Model)            —— 平台对外暴露的模型，有 model_id、分类、图标
  └─ 渠道 (Deployment)  —— 一个具体的上游接入点：绑定凭证 + litellm_params + 定价
                          一个模型可有多个渠道（多供应商/多凭证负载均衡）
凭证 (Credential)       —— 供应商 API Key + api_base，可复用
路由配置 (RouterSettings) —— 全局路由策略、重试、超时、Fallback 链
访问组 (AccessGroup)    —— 把一组 model_id 打包，便于批量授权
```

**一个模型必须有至少一个「可路由的渠道」才能真正被调用。** 建模型只是建了个壳。

## 3. 建渠道：高级配置全在这里

路径：admin → 模型管理 → 选模型 → 渠道 → 新建/编辑 → **「高级设置」**（折叠区）。

高级设置分四块：**路由 / 超时 / 计费方式 + 定价 / 透传**。下面逐块说明每个字段填什么、落到哪。

### 3.1 路由（部署级）

控制同一 model group 内**多个渠道之间**怎么分流。

| 前端字段 | 落到 `litellm_params` 的 key | 含义 |
|---------|------------------------------|------|
| 权重 | `weight` | 路由权重，默认 1。多渠道时按权重比例分流 |
| 优先级 | `order` | 数字越小越优先，主渠道故障才用高 order 的备用渠道 |
| 标签 | `tags` | 逗号分隔，转数组。用于按标签路由（如 `canary`、`internal`） |

> 这是**部署级**路由。**全局**路由策略（轮询/最低成本等）在另一处配，见第 4 节。

### 3.2 超时与重试（部署级）

| 前端字段 | `litellm_params` key | 含义 |
|---------|----------------------|------|
| 超时 (秒) | `timeout` | 单次请求超时，默认 30 |
| 流式超时 | `stream_timeout` | 流式响应的超时，可选 |
| 最大重试 | `max_retries` | 本渠道重试次数，默认 2 |

部署级超时会**覆盖**全局超时（第 4 节）。

### 3.3 计费方式（关键）

`计费方式` 下拉三选一，决定这个渠道**成本怎么算**：

| 选项 | `billing_type` | 定价字段 | 适用 |
|------|----------------|----------|------|
| Token 计费 | `token` | 按 token 单价（¥/百万 token） | 绝大多数按量计费模型 |
| Token Plan（按次计费） | `per_call` | 单次费用（¥/次） | 打包按次计费 |
| Token Plan（包月次数） | `monthly_quota` | 单次费用（¥/次）+ 月配额 | 包月套餐 |

### 3.4 定价（成本管理的核心）

定价分**外部官方定价**和**内部结算定价**两套，互相独立：

**外部官方定价**（`billing_type=token` 时显示）—— 你向上游供应商付的钱。

单位统一是 **¥/百万 token**。

| 前端字段 | `litellm_params` key | 说明 |
|---------|----------------------|------|
| 输入 | `input_cost_per_token` | 输入 token 单价 |
| 输出 | `output_cost_per_token` | 输出 token 单价 |
| 缓存读取 | `cache_read_input_token_cost` | 命中上下文缓存的输入单价，可选 |
| 缓存写入 | `cache_creation_input_token_cost` | 写入缓存的输入单价，可选 |

> **单位换算（重要）**：前端填的是 **¥/百万 token**，但同步到 LiteLLM 时会被 `_convert_cost_for_litellm` 转成 **USD/token**（LiteLLM 原生单位）。公式：`USD/token = 填充值 / usd_to_cny_rate / 1_000_000`（`model_service.py:316`）。
>
> `usd_to_cny_rate` 在 `core/config.py` 默认 **7.0**，通过环境变量 `USD_TO_CNY_RATE` 调整。**改这个汇率会影响所有历史定价的换算**，调前想清楚。

**内部结算定价**（落到 `model_info`，平台自己算账用，**不进 LiteLLM**）—— 你向内部部门/项目收的钱。

`billing_type=token` 时填 `internal_input_cost / internal_output_cost / internal_cache_read_cost / internal_cache_creation_cost`（¥/百万 token）；
`per_call / monthly_quota` 时填 `internal_cost_per_call`（¥/次）。

外部定价和内部定价可以不同，实现「买进价 vs 内部结算价」的差价管理。

**按次计费**（`per_call / monthly_quota`）的「单次费用」填在外部「外部单次定价」→ `cost_per_call`（¥/次）。

### 3.5 透传

| 前端字段 | `litellm_params` key | 含义 |
|---------|----------------------|------|
| 透传 | `use_in_pass_through` | 直接透传请求，**开启后 RPM/TPM 限流不生效**（前端有黄字提示） |
| 丢弃不支持参数 | `drop_params` | 上游不支持的参数自动丢弃，而非报错 |

## 4. 全局路由配置

路径：模型管理页右上角 **「路由配置」** 按钮。

同步到 LiteLLM 的 `router_settings`，是**全局**路由行为，作用于所有 model group。

| 前端字段 | key | 默认 | 含义 |
|---------|-----|------|------|
| 路由策略 | `routing_strategy` | `simple-shuffle` | 见下表 |
| 连续失败摘除 | `allowed_fails` | 3 | 渠道连续失败几次后摘除（进冷却） |
| 冷却时间 (秒) | `cooldown_time` | 60 | 摘除后多久再放回路由池 |
| 全局重试次数 | `num_retries` | 2 | 全局默认重试 |
| 全局超时 (秒) | `timeout` | 30 | 全局默认超时（被部署级 timeout 覆盖） |
| Fallback 链 | `fallbacks` | `[]` | 主模型故障时降级到备模型，如 `glm-5.1 → deepseek-v4-flash` |

默认值见 `model_service.py:593`。

**路由策略五选一**：

| 值 | 前端文案 | 行为 |
|----|---------|------|
| `simple-shuffle` | 轮询 | 按权重随机轮询（默认） |
| `latency-based-routing` | 最低延迟 | 优先打历史响应快的渠道 |
| `cost-based-routing` | 最低成本 | 优先打便宜的渠道（**依赖第 3.4 节定价填对**） |
| `least-busy` | 最少使用 | 优先打当前并发最低的渠道 |
| `usage-based-routing` | 按用量均衡 | 按 TPM/RPM 用量均衡分配 |

> **`cost-based-routing` 想生效，必须把每个渠道的外部定价填全**，否则 LiteLLM 无法比较成本。这是常见坑。

**Fallback 链**示例：源模型 `glm-5.1`，Fallback 模型 `deepseek-v4-flash, kimi-k2.6`，表示 glm-5.1 全部渠道都失败时，依次降级到这两个模型。

## 5. 发布与可见性

模型配好了渠道，还要**发布**才能被用户看到/申请。

路径：模型列表 → 操作 → **发布设置**。

| 字段 | 含义 |
|------|------|
| `is_published` | 是否上架到 web 端市场 |
| `visibility_type` | `all` 全员可见 / `selected` 按部门可见 |
| `requires_approval` | 用户申请使用是否需要审批 |

发布规则（`model_service.py:781`）：**已发布 + 免审批 + 启用**的模型，会自动同步进**所有主 Key** 的 models 列表，用户立即可用。反之（取消发布/需审批/禁用）会从主 Key 移除。

## 6. 成本数据从哪来

这是运维最常被问的问题：「我填的定价，最后怎么变成报表里的数字？」

```
1. 用户调用 → LiteLLM 路由到渠道 → 上游供应商响应
2. LiteLLM 记录本次调用的 usage(token 数) + 按 litellm_params 定价算 spend(USD)
3. 平台定时任务拉取 LiteLLM 的 usage/log → 落 llm_call_logs
4. 平台按【内部结算定价 model_info.internal_*】重新算成本 → cost_summary_daily
5. 成本中心 / 看板 只读平台 DB 的这两张表
```

要点：

- LiteLLM 自己会按**外部官方定价**（已转成 USD/token）算 spend，但平台**不直接拿这个数做业务展示**；
- 平台成本口径用 **`model_info` 里的内部结算定价**，单位 ¥/百万 token，不经过 USD 换算；
- 所以**内部结算定价填没填、填得对不对，直接决定成本报表准不准**。没填则该渠道成本可能为 0；
- 汇率 `usd_to_cny_rate` 只影响「外部定价 → LiteLLM spend」的换算，不影响平台内部结算口径。

### 6.1 排查「成本为 0」

按顺序查：

1. 渠道**内部结算定价**有没有填（第 3.4 节）—— 最常见原因；
2. 渠道和凭证是否都 `is_active`（被禁用的渠道不产生新调用）；
3. LiteLLM usage 拉取任务是否在跑（看 celery worker 日志）；
4. `llm_call_logs` 里有没有这个模型的记录。

## 7. 验证：配置完后怎么测对不对

### 7.1 单点连通性测试（admin 内置）

模型管理 → 渠道列表 → **测试**，或「连通性测试」入口。后台走 `/access-test/test`（`api/v1/access_test.py`），用当前管理员的主 Key 打一次，支持流式。这是**验证单个渠道**最快的方式。

### 7.2 批量模拟真实流量（推荐用于成本/路由验证）

项目自带脚本：`dev/resource/gateway_traffic_simulator.py`

作用：直连 LiteLLM 网关，对所有模型同时模拟真实用户调用（不同模型并行、同模型串行、随机间隔/随机 prompt/随机 max_tokens、随机流式），用来：

- 验证多渠道**负载均衡 / 路由策略**是否生效；
- 产生足够量的 usage，**喂给成本中心**看报表是否正确；
- 同时压 OpenAI 和 Anthropic 两套协议。

用法：

```bash
# 1. 改脚本顶部配置（BASE_URL / API_KEY / MODELS）
# 2. 运行
python dev/resource/gateway_traffic_simulator.py
```

流程：先跑**连通性测试**（每个模型 × 两种协议各打一次，输出 ✓/✗ 矩阵）→ 通过后**按回车**手动启动模拟 → `Ctrl+C` 停止。

脚本只依赖 Python 标准库，无需装包。控制台每行打印一次调用的协议、模型、输入/输出 token、延迟，方便对照 LiteLLM 和平台日志。

> 跑完等几分钟（等平台拉取任务跑一轮），再去成本中心/日志管理看数据是否对得上。

## 8. 新模型上线 checklist

按顺序做，每步对应手册章节：

1. **建凭证**（供应商管理）：填 API Key、api_base，格式选 `openai` 或 `anthropic`，确认 `is_active`；
2. **建模型**：填名称、model_id（后续两种协议都基于它）、分类（chat/embedding/rerank）、图标；
3. **建渠道**（核心）：
   - 选关联凭证、填厂商模型名称（`litellm_params.model`）；
   - 配**计费方式**（3.3）；
   - 配**外部官方定价 + 内部结算定价**（3.4）—— 别漏内部定价，否则成本为 0；
   - 按需配路由/超时（3.1、3.2）；
4. **连通性测试**（7.1）确认渠道通；
5. **发布**（第 5 节）：设可见性、是否需审批；
6. **全局路由**（第 4 节）：多渠道时配策略/Fallback；
7. **跑模拟脚本**（7.2）造流量，验证成本报表。
