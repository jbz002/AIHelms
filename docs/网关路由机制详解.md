# 网关路由机制详解（问答）

针对「模型管理」里路由相关配置的概念澄清。配合 [网关与成本管理配置手册](网关与成本管理配置手册.md) 一起看。

---

## 0. 先搞清：部署级路由 vs 全局路由

这是最容易混的点，先讲透。

平台路由配置分两层，作用范围完全不同：

| | 全局路由 (RouterSettings) | 部署级路由 (每个渠道的 `litellm_params`) |
|---|---|---|
| 配在哪 | 模型管理页右上角「路由配置」按钮 | 每个渠道编辑表单的「高级设置 → 路由/超时」 |
| 管谁 | **整个平台所有 model group** 的总调度规矩 | **只管这一个渠道**在自己 group 内怎么被挑 |
| 回答的问题 | 「整体怎么调度？失败了怎么办？」 | 「我这个渠道跟同 group 的兄弟渠道比，咋分工？」 |
| 典型字段 | 路由策略、全局重试次数、全局超时、失败摘除阈值、Fallback 链 | 权重、优先级、标签、单渠道超时 |
| 几份 | 全平台**一份** | **每个渠道**一份 |

**通俗打比方——餐厅**：

- **全局路由 = 餐厅的整体派单规矩**：「先来先服务（轮询）」「谁出菜快就多派给谁（最低延迟）」「某厨师连着做砸 3 次就让他歇 5 分钟（连续失败摘除）」「主厨不在就让二厨顶上（Fallback）」。全店一套规矩。
- **部署级路由 = 某个厨师自己的设定**：「我擅长辣菜，多给我派辣单（权重）」「我只是备用的，主力在就别叫我（优先级）」「我只做素食（标签）」「我做一道菜最多 20 分钟（单渠道超时）」。

一句话区别：**全局是「策略层」决定怎么调度，部署级是「参与者层」决定自己怎么被卷入调度。**

一个渠道最终被不被命中，是「全局策略怎么挑」×「这渠道自己的权重/优先级/标签」共同决定的。

## 1. 部署级路由：权重 / 优先级 / 标签

前提：一个**模型**下挂多个**渠道**（deployment）= 同一 model group 里多个上游。这三个字段管的是「group 内怎么挑渠道」。举例用 `glm-5.1` 挂两个渠道：A=官方直连、B=代理供应商。

### 权重 (weight)

在「都能用」的渠道间**按比例分流量**。

- A `weight=3`，B `weight=1` → 75% 打 A、25% 打 B。
- 只在 `simple-shuffle` / `usage-based` 这类按权重路由的策略里生效；`cost-based` / `latency-based` 各自另算。
- 用途：A 便宜稳，B 贵但兜底 → 多给 A、少给 B。

### 优先级 (order)

数字小**先试**，小的挂了才用大的。**不是分流量，是分梯队**。

- A `order=0`（主），B `order=10`（备）→ 平时全部打 A，A 没掉链子 B 一点流量都没有。
- 只有 A 被「连续失败摘除」（进冷却）后，B 才顶上。
- 用途：主备容灾，平时只用主渠道。

> 权重和优先级是两套脑子别混：**权重** = 同一梯队内分蛋糕；**优先级** = 梯队顺序，前面梯队全废才轮到后面。

### 标签 (tags)

给渠道打标，**按标路由**。

- A 打 `stable`，B 打 `canary` → 路由时可指定「只发 canary 渠道」，灰度新供应商不碰正式流量。
- 也可 `internal` / `external`、`region-cn` / `region-us` 分流。
- 用途：灰度发布、内外区隔、A/B。

## 2. 「部署级超时覆盖全局超时」怎么理解

全局 `RouterSettings.timeout=30s` 是**给所有渠道的默认值**。
某个渠道单独填 `litellm_params.timeout=60s`，**只这个渠道**用 60s，其余渠道还是 30s。

「覆盖」= 有局部值时局部说了算，没局部值就回落到全局。不是把全局改成 60。就像 Bash：全局环境变量 `TIMEOUT=30`，某个进程自己 `export TIMEOUT=60`，只影响它自己。

为何要这个能力：慢模型（长文生成长输出）需要更长超时，快模型保持短超时。一刀切会误杀或拖垮。

## 3. 透传 (use_in_pass_through)

正常 LiteLLM 是「聪明中间人」：解析你请求 → 挑渠道 → **限流计数（RPM/TPM）→ 算 token/spend** → 转发给上游 → 再处理响应回来。

透传 = 告诉 LiteLLM「别聪明了，原样转发」。它变根**管子**，请求几乎不解析直接捅给上游。

- 好处：上游支持但 LiteLLM 不认的参数照传不误，格式零损失，兼容性好。
- 代价：LiteLLM 那套保护逻辑绕过——**限流（RPM/TPM）不生效**（所以前端黄字警告）、虚拟 Key 的模型限制也可能放松。

一句话：**透传换兼容，代价是限流失效**。给稳定标准接口别开；给某些特殊原生参数、LiteLLM 解析有 bug 的接口才开。

## 4. allowed_fails=3 vs num_retries=2 不冲突

这俩是**两个层级**的机制，不在一条路上比大小。

### num_retries=2（每次请求的重试预算）

- 某次调用失败 → 重试，最多重试 2 次（总共最多打 3 次请求）。
- 管的是「单次请求别轻易放弃，换渠道/同渠道再试」。
- 维度：**单次请求**。

### allowed_fails=3（单个渠道的健康线）

- 某**渠道**累计失败到 3 次 → 把它**摘除**（进冷却 `cooldown_time` 秒，期间不给它派活）。
- 管的是「这渠道是不是坏透了，先晾它」。
- 维度：**单个渠道的累计健康度**。

### 两者关系（举例）

1. 请求打渠道 A，A 挂 → A 失败计数 +1（=1）；
2. num_retries 让路由重试，可能换到 B 成功，或又打到 A 再挂 → A 计数 +1（=2）；
3. 后续别的请求再来，A 又挂 → A 计数 =3，**触发摘除**，进冷却。之后路由自动绕开 A，全给 B。

所以 `num_retries=2 < allowed_fails=3` **完全正常**：意思正是「单次请求给你重试 2 次的容忍，但某个渠道累计扛到第 3 次失败，我就认定它坏了，拔掉」。

重试是**请求级**的临时补救，摘除是**渠道级**的长期隔离——前者小、后者大，没矛盾。真要冲突的样子是反过来的设定才有问题（比如重试次数极大而摘除阈值=1），默认值这套是合理的。

## 5. 凭证 vs 部署（术语别混）

- **凭证 (Credential)** = `api_key + api_base` 的认证包，按供应商建一次，可被多部署复用。
- **部署 (Deployment)** = 把一个模型绑到一个凭证上 + 路由/定价配置。一个模型可挂多个部署。

「一个模型建两个部署」≠「建两个凭证」。凭证只建一次，部署才按需多个。

## 6. 一个模型两种协议 = 两个独立路由池

给同一模型挂一个 openai 部署 + 一个 anthropic 部署，平台同步到 LiteLLM 时按凭证格式给 model_name 加后缀（`_get_litellm_model_name`，`model_service.py:745`）：

- openai 部署 → LiteLLM model_name = `spark-v4`
- anthropic 部署 → LiteLLM model_name = `spark-v4(Anthropic)`

`(Anthropic)` 后缀就是**把它们拆成两个互不相干的路由池**的手段。同名才算一个池。

### 用户请求怎么落池（用户决定，无协议转换）

用户的 `model` 字段 + 打的端点，**确定性**选池：

| 用户打 | model 字段 | 落进哪个池 | 只能路由到 |
|--------|-----------|-----------|-----------|
| `/v1/chat/completions` | `spark-v4` | openai 池 `spark-v4` | openai 格式渠道 |
| `/v1/messages` | `spark-v4(Anthropic)` | anthropic 池 `spark-v4(Anthropic)` | anthropic 格式渠道 |

**用户选了 openai，绝不可能路由到 anthropic 渠道**。两个池互相看不见，没有「内部转换、用户无感」——那是另一类协议适配网关，本平台不干。

### 为什么要建两种协议部署

不是为路由容灾，是**客户端兼容**：Cursor/openai SDK 只会打 `/v1/chat/completions`，Claude Code/anthropic SDK 只会打 `/v1/messages`。同一底层模型开两种方言入口，让不同客户端都能接。没人用某种协议，就不建那个池。

### 跨协议能 fallback 吗

LiteLLM `fallbacks` 是「group → group」降级，理论上能配 `spark-v4 → spark-v4(Anthropic)`。但实际**不推荐**：fallback 不自动转请求体格式，openai 请求捅到 anthropic 渠道大概率报错。fallback 留给「同协议、换模型」（如 `glm-5.1 → deepseek-v4-flash`，都 openai）。

---

## 7. 路由何时才生效：同池 ≥2 渠道

权重/优先级/策略，**只在一个池里有 ≥2 个渠道时**才有意义。

```
openai 池 spark-v4 = { 渠道①(供应商A, weight 2), 渠道②(供应商B, weight 1) }  ← 同池，权重分流量
anthropic 池 spark-v4(Anthropic) = { 渠道③ }                                 ← 单渠道，路由特性闲置
```

- 池 spark-v4 里①②是同协议、都服务该模型的多个上游 → `simple-shuffle` 按 weight 在①②间分。
- 池 spark-v4(Anthropic) 只有③ → 没东西可分，权重/策略空转，每次都打③。

要让路由跑起来，得有**第二个来源也能调同一模型**（如官方 + 代理商都卖 glm-5.1），挂两个同格式渠道。

## 8. 路由分组看哪个字段：模型 ID

三个字段别混：

| 前端字段 | 落库 | 作用 | 影响分组？ |
|---------|------|------|-----------|
| 模型名称 | `Model.name` | 纯展示 | 否 |
| **模型 ID（用户请求时使用）** | `Model.model_id` | **路由分组名 + 用户 `model` 字段匹配值** | **是** |
| 厂商模型名称 | `litellm_params.model` | LiteLLM 调上游时发的真实模型标识（如 `spark-v4`） | 否 |

路由分组名 = `model.model_id`（`_get_litellm_model_name` 直接用它）。用户请求时 `model` 字段也匹配它（`access_test.py:61`）。厂商模型名只是上游调用标识，不影响分组。

### 同池判定

**同一个平台模型（同 `model_id`） + 同凭证格式 = 同一个路由池。**

```
平台模型「spark-v4」(model_id = spark-v4)
├─ 部署①  凭证=openai-A   → 池 spark-v4        ← 同池，权重分流
├─ 部署②  凭证=openai-B   → 池 spark-v4        ← 同池
└─ 部署③  凭证=anthropic  → 池 spark-v4(Anthropic)  ← 另一池
```

想让多个渠道进同一池，它们的「模型 ID」必须填**同一个值**。填不一样就散成多个池，路由失效。哪怕厂商模型名填得不同，只要同模型同格式仍同池（但通常填一致才合理）。

## 9. 实战：讯飞 coding plan 正交 key 接入

讯飞 coding plan 给两个端点，各两个 key：

- `/v2`（openai 格式）：`https://maas-coding-api.cn-huabei-1.xf-yun.com/v2`
- `/anthropic`（anthropic 格式）：`https://maas-coding-api.cn-huabei-1.xf-yun.com/anthropic`

**关键前提：两个 key 可调的模型正交不重叠**（key1 能调 {A,B}，key2 能调 {C,D}）。

### 9.1 正交 key 改变了一件事

正交 = 一个模型只被一个 key 拥有 → 同格式同模型只能挂 1 个渠道 → **路由特性用不上**（池里就 1 个渠道）。这是正常的，不是配置错。

每个「模型 × 协议」绑**拥有它的那个凭证**，正好一个。不要为同一模型同协议建第 2 个部署——另一个 key 调不动它，绑上去是死渠道。

### 9.2 供应商与凭证怎么建

**供应商**（1 个）：

| 字段 | 值 |
|------|----|
| name | `讯飞星火` |
| provider_type | `xunfei`（需加 prefix_map 迁移，见 9.4） |

**凭证**（按 key × 协议组织，key 正交所以按套餐命名）：

| 凭证名 | format | api_base | key |
|--------|--------|----------|-----|
| `讯飞-coding-openai-套餐A` | openai | `…/v2` | openai key1（管 A、B） |
| `讯飞-coding-openai-套餐B` | openai | `…/v2` | openai key2（管 C、D） |
| `讯飞-coding-anthropic-套餐A` | anthropic | `…/anthropic` | anthropic key1（管 A、B） |
| `讯飞-coding-anthropic-套餐B` | anthropic | `…/anthropic` | anthropic key2（管 C、D） |

`credential_info` 必带 `{"format": "openai"}` 或 `{"format": "anthropic"}`，平台靠它决定加不加 `(Anthropic)` 后缀。

### 9.3 部署怎么挂

每个模型两个部署（openai + anthropic），各绑拥有它的凭证：

| 模型 | openai 部署 → 凭证 | anthropic 部署 → 凭证 |
|------|---------------------|------------------------|
| A | 套餐A | 套餐A |
| B | 套餐A | 套餐A |
| C | 套餐B | 套餐B |
| D | 套餐B | 套餐B |

anthropic 部署按需建——没用户走 anthropic 协议就省掉。建完每个部署用 admin「连通性测试」打一次，确认 key 确实拥有该模型。

### 9.4 prefix_map 迁移（关键）

讯飞不在内置 `provider_prefix_map`，需加迁移（参考 `006_add_xiaomi_mimo_prefix_map.sql`）：

```sql
INSERT INTO aihelms.provider_prefix_map (provider_type, format, category, prefix, needs_v1)
VALUES
  ('xunfei', 'openai',    'chat', 'openai',    false),
  ('xunfei', 'anthropic', 'chat', 'anthropic', false)
ON CONFLICT (provider_type, format, category) DO NOTHING;
```

**`needs_v1=false` 必须**：api_base 已含完整 `/v2` 或 `/anthropic` 路径，`needs_v1=true` 会让平台再补 `/v1` 把路径搞错（`_ensure_v1_suffix`，`model_service.py:1001`）。

按项目规则，加供应商还要同步：前端供应商选项加 `xunfei`、补 provider 图标 + 后端 `logo_provider_type` 映射 + shared `getProviderIconUrl` 映射。

### 9.5 api_base 路径验证

- openai 端点填到 `/v2` 为止（LiteLLM 会拼 `/v2/chat/completions`），**别带 `/chat/completions`**。
- anthropic 端点填到 `/anthropic` 为止（LiteLLM 拼 `/v1/messages`）。此处不同 LiteLLM 版本行为略有差异，建完用连通性测试验证；404 多半是 api_base 后缀问题，试调成 `…/anthropic/v1` 或调 `needs_v1`。
