# AI Hub 统一鉴权接入：6 种方式的心智模型（通俗版）

> 2026-09-11。配套手册：`.claude/skills/ai-hub/SKILL.md`（接入手册，含代码模板与端点表）。
> 本文只建心智模型：读完你应该能自己回答"如果 X 发生，会怎样"这类手册没直接写的推论题。

## 一、总原则（一句话总纲）

**AI Hub 是公司唯一的发卡处：所有凭证都是它签的，应用之间从不互发凭证；谁想确认"来者是谁"，就打电话问发卡处。**

6 种方式不是 6 套平行系统，是这一条原则在 6 个不同接触点的用法：

```
用户进应用（4 种进门姿势）：方式一 / 二 / 三 / 四
应用以自己身份调 AI Hub：方式五
应用之间互调（或被调，或调 AI Hub）：方式六
```

记不住细节时想两个问题：「谁在进（人还是应用）」「从哪进（同一栋楼还是隔着马路）」——答案自动落在某个方式上。

## 二、角色模型

把整套系统看成**一栋大楼的门禁体系**：

| 故事角色 | 真实系统 | 说明 |
|---|---|---|
| 行政中心（发卡处） | AI Hub | 唯一的发凭证方。只有它知道每个员工是谁、什么部门、能进哪 |
| 员工 | 用户 | 人在各楼层间走动 |
| 楼内各楼层/各公司 | 各子应用（ai-assistant、aihelms、ai-chat……） | 每层有自己的业务，认卡不认人 |
| 工卡（30 分钟后消磁） | access_token | 用户的临时身份凭证，有效期 30 分钟 |
| 续卡凭证 | refresh_token | 30 分钟到了凭它换新工卡，不用回行政重排队 |
| 一次性通行条（30 秒） | ticket | 方式三用：跨楼入场的一次性纸条，用过作废 |
| 一次性取号单（60 秒） | authorization code | 方式四用：凭它与行政换正式工卡 |
| 部门公章（ak- 开头） | AppAPIKey | 应用以"部门"而非"某个人"的身份行文，绑定 app_code |
| 门卫电话核实 | introspect（`GET /api/v1/auth/introspect`） | 被调方收到凭证后，原样转给行政问："这是真卡吗？是谁的？" |
| 楼层闸机 | nginx auth_request | 方式二里每进一个楼层自动刷卡 |
| 连体楼层 | qiankun 主应用+微前端子应用 | 同一个 SPA，物理上不用二次过门禁 |
| 楼内自制胸牌 | 子应用本地 JWT | 应用发给自己会话用的内部凭证，与行政的卡互不相认 |

```
                 ┌──────────────┐
                 │   AI Hub     │  ← 唯一发卡处（签发一切凭证）
                 │  行政中心     │
                 └──┬───────┬───┘
        用户凭证(工卡/通行条/取号单)  应用凭证(部门章)
           │                        │
   ┌───────▼────────────────────────▼───────┐
   │  子应用们（各楼层）                        │
   │  内部用自制胸牌(本地JWT)管自己人            │
   │  楼层之间互调 → 打电话问行政(introspect)   │
   └────────────────────────────────────────┘
```

## 三、主流程：张三的一天

跟一个最小单元走完：**一个员工从上班到下班，6 种方式各在哪里出现。**

**早上 9:00，张三打开公司工作台。** 输一次账号密码（或钉钉扫码）——这是全公司唯一一次登录。
行政中心给他一张工卡（access_token）+ 一张续卡凭证（refresh_token），并写入浏览器 Cookie。

**9:01，他点工作台里的「企业 AI 助手」卡片**（方式三，ticket）：AI Hub 生成一张 30 秒一次性
通行条，浏览器带着 `?ticket=xxx` 跳到 ai-assistant 的门卫室（后端路由 `/oauth/aihub/ticket`）。
ai-assistant 拿通行条去行政中心核对（`POST /verify-ticket`，用后即焚），行政说"是真员工张三，
普通员工、研发部"。ai-assistant 于是在自己的楼里给张三建档案、发**本楼胸牌**（本地 JWT）——
之后张三在 ai-assistant 里的一切动作，只认这枚胸牌，不再打扰行政。

**10:00，张三没经过工作台，直接在浏览器新标签页打开 AIHelms**（方式四，OAuth2）：
没人发通行条，怎么办？AIHelms 发现他没胸牌，把他整个人重定向到行政中心刷脸。张三的
Cookie 还在（上午登过），行政中心**静默**核对完——连界面都没弹——给他一张 60 秒一次性
取号单（`?code=xxx`）送回 AIHelms 的 callback 路由。AIHelms 拿取号单跟行政换正式资料 +
新工卡（`POST /token`），然后照旧建档案、发胸牌。两次跳转，张三全程无感。

**10:05，张三在 ai-assistant 里发起对话。** ai-assistant 需要他个人的模型 key，就拿着
**张三的工卡**（不是自己的部门章！）直连 AIHelms：`GET /integration/identity`。
AIHelms 收到后**不自己看卡**，而是拿这张卡原样打给行政中心：`GET /auth/introspect?app_code=aihelms&target_path=...`（方式六，被调方姿势）。行政核实："真卡，持卡人张三，个人凭证"，
AIHelms 才把张三的 key 递出去。这就是应用间调用的全部信任来源：**AIHelms 从不问对方
"你是谁"，只问行政"来人手里的卡是谁的"。**

**10:30，ai-assistant 后台任务想拉公司部门列表**（方式五，AppAPIKey）：没有具体用户在场、
张三的工卡 30 分钟就消磁，不能拿来跑后台定时任务。ai-assistant 用**自己盖了部门公章
（`ak-` 开头的 key，绑定 app_code）**调 AI Hub 的 `/api/v1/common/*`。行政看章不看人：
章是真的、绑的是 ai-assistant，就办。

**11:00，张三工卡到点消磁。** ai-assistant 里某接口返回 401 → 前端拿续卡凭证调
`POST /auth/refresh` 静默换新卡 → 重试刚才的请求。张三无感；续卡凭证也没了 → 重跳
authorize（Cookie 还在，又是静默）。

**下午，AIHelms 的管理后台被 AI Hub 平台调用**（还是方式六）：平台聚合待办要拉 AIHelms
数据，带平台统一持有的凭证来。AIHelms 同样 introspect 一遍——行政报出"这是平台章
（app_code=ai-hub）"或"这是代理张三的卡"——AIHelms 按来电身份决定给全量数据还是仅个人数据。
**平台调用你不需要任何额外配置**：它用的也是发卡处自己签的卡。

## 机制组（每个方式 = 问题 + 解法 + 代价）

### 方式一：qiankun props —— 连体楼层直接抄名条

- **问题**：公司有 20 个应用，若每个都让用户登一遍，20 次账号密码、20 套会话，体验崩溃。
  其中 qiankun 微前端这种形态更尴尬：子应用是嵌在主应用页面里的 iframe/组件，根本没有
  独立 URL 可跳登录。
- **解法**：主应用已经过了门禁，就把用户的身份信息（token、姓名、角色、部门）**作为 props
  直接塞给子应用**。子应用 mount 时接住存进自己的 Context。
- **代价**：仅限同一 SPA 内的微前端形态；子应用离开主应用单独打开时这条通道失效——所以
  独立入口的应用别选这条。
- 对应的信任结构：props 是主应用背书的（主应用自己已过门禁），子应用不再核身。

### 方式二：Cookie + nginx —— 同域共用一张门禁卡

- **问题**：另一批应用**独立部署但与 AI Hub 同域**（同一域名下）。浏览器里 Cookie 天然跨
  子域共享，这是现成的共享登录态——但后端不能对每个请求都自己去行政中心核一遍（太慢）。
- **解法**：nginx 闸机统一拦在门口：每个请求先走 `auth_request` 打一次 AI Hub 的
  `/auth/verify` 核 Cookie，通过后把 `X-User-Id`/`X-User-Role`/`X-App-Roles` 三个头注入，
  转发给应用。应用看头干活，不再自己验。
- **代价**：① 只在同一域下可行——**同 IP 不同端口也是跨域**，Cookie 不通，此路封死；
  ② `X-App-Code` 头可被伪造，闸机必须从 URI 前缀解析应用（`/subapps/{code}/`），不能信头。
- 这类应用的配置由 AI Hub `GET /api/v1/apps/nginx-config` 自动生成，不手写。

### 方式三：Ticket —— 一次性通行条（从工作台跳转进来）

- **问题**：应用与 AI Hub 跨域（IP 相同端口不同也算），Cookie 共享不了；但用户是从
  AI Hub 工作台**点卡片进来**的——这次入场需要一个能"跨楼携带"的凭证，又要防止被
  URL 里截获后反复使用。
- **解法**：一次性通行条（ticket）：**30 秒有效、用后即焚**。应用后端拿它调
  `verify-ticket` 换用户信息，然后发本楼胸牌。跨楼传递的暴露窗口只有 30 秒，且一次性。
- **代价**：① 用户必须从工作台进来——直接打开应用 URL 没人发条，此路不通（所以有方式四）；
  ② 30 秒意味着跳转链路要快；③ React StrictMode 的 useEffect 跑两遍会把同一张条消费两次
  → 第二次 401，前端要拿 `Set` 缓存已验证的 ticket。
- 想要"张三在你这层的角色标签"（app_roles），验证时带 `app_code`，行政会一并返回。

### 方式四：OAuth2 授权码 —— 自己开门的用户（★推荐）

- **问题**：方式三的前提是"从工作台点进来"。但用户可能**直接在浏览器输你的应用 URL**
  （新标签页、收藏夹、别人发的链接），此时没有通行条、没有同域 Cookie。应用需要一个
  独立入口，还得支持"用户本来就没登录"的情况。
- **解法**：应用发现用户没胸牌 → 把他重定向到行政中心的 `/authorize`：
  - 已登录（Cookie 在）→ **静默**校验该用户有没有权限进这个应用（`required_permissions`
    白名单）→ 发一张 60 秒一次性取号单（code）→ 307 跳回你预设的 callback URL；
  - 未登录 → 先弹登录页，登录后接着走，用户感知只是"多输了一次密码"；
  - 白名单不满足 → 停在行政的无权限页，**不发号**，你就收不到 code（访问控制前移到了
    AI Hub，应用端无感）。
  应用后端拿 code 调 `/token`，换回**用户信息 + 工卡 + 续卡凭证**三件套，然后发本地胸牌。
- **代价**：① 回调 URL 必须精确 URL 编码；② code 只能由**后端**去换（前端直接 GET `/token`
  是常见翻车点）；③ StrictMode 双执行同样会炸一次性 code。
- **方式三 vs 四怎么选**：只有"从工作台进入"一种入口 → 三；需要独立入口（用户可能直接打开）
  → 四。两者代码骨架同构（检测 URL 参数 → 后端换取 → 发胸牌），可以两个都留。

### 方式五：AppAPIKey（`ak-`）—— 部门公章

- **问题**：工卡是**人**的凭证，30 分钟就过期，且"个人数据"语义太强。应用有些调用根本
  没有具体用户在场：定时任务拉部门列表、后台聚合统计——这些是**应用自己在行文**，不是
  代理某个人。
- **解法**：应用在行政中心刻一枚**部门公章**（服务级 API Key，`ak-` 前缀，绑定本应用
  app_code），以后以应用身份调 AI Hub 的 `/api/v1/common/*` 一律盖这个章。
- **代价与边界**：公章的语义是"应用自身"——**禁止拿公章去查个人数据**。AI Hub 签发的
  公章调别人应用的个人接口时，对方按 `caller_type=app` 处理，个人数据接口会直接 403
  （AIHelms 的 identity 接口就是这么拒的）。个人语义的调用必须用用户的工卡。

### 方式六：直连 + introspect —— 应用之间互调（★强制）

- **问题**：这是整套体系里最容易被想歪的地方。A 应用要调 B 应用的接口，最直觉的做法是
  "A、B 事先共享一个密钥，A 每次请求带签名"。这么干会立刻撞上三堵墙：
  ① N 个应用互调要 N×(N-1)/2 把共享密钥，矩阵爆炸；② 任何一把泄漏要所有相关方换钥；
  ③ AI Hub 完全看不见这些调用——**集中审计失效**，这违反"公司只有一个发卡处"的总纲。
- **解法**：**凭证照旧由行政签**，B 收到请求后不自己判断，把收到的凭证**原样**打给行政的
  `/auth/introspect`，问三件事：卡是真的吗？持卡是人还是章？是哪个应用/哪个人？行政返回
  `caller_type=user/app` + `user_id/app_code`，B 据此放行，并把 `target_path`/`method`
  一并传去——行政顺手把这条调用记进**调用日志**（谁、何时、调了谁、哪个接口、结果、来源
  IP，留 90 天）。
  凭证本身仍是三选一：用户工卡（代理该用户）、调方自己的公章、平台统一凭证。**A 从不问
  B 要密钥，B 从不自己验卡。**
- **代价**：① 每次调用多一跳 AI Hub 网络请求——高频接口应按凭证做 60 秒 TTL 缓存；
  ② AI Hub 变成调用路径上的可用性依赖（它挂则互调全停，与登录同命运）；
  ③ 每次自省落一条调用日志（这是特性不是负担——审计对账就靠它）。
- **两个授权开关**（都在行政侧配置，代码零改动）：B 能不能被调，看 A 的
  `allowed_target_apps` 勾没勾 B（未勾 → introspect 直接 403）；持工卡的人能不能进 B，
  看 B 的 `required_permissions` 白名单。
- **备选姿势：AI Hub 代理转发**（`/api/v1/proxy/{对方code}/{path}`）：前端不方便直连对方
  时，可以打 AI Hub 让它转。适合低频管理类调用；高频业务调用仍走直连 + 自省（代理是
  方式六的备选姿势，不是第七种方式）。

### 应用怎么保护自己的接口（凭证矩阵收尾）

到这里所有进站流量只有两类凭证，应用只需各配一道门：

| 来客 | 用什么 | 应用怎么处理 |
|---|---|---|
| 浏览器里的用户 | 本地胸牌（SSO 换来的本地 JWT） | 本地验签依赖，管业务权限 |
| 其他应用 / AI Hub 平台 | AI Hub 签发的凭证 | **一律 introspect**（方式六），按 `caller_type` 分流：user → 代理该用户操作，app+ai-hub → 平台服务身份，其他 app → 对方应用服务态 |

## 已知缺口（诚实清单）

- **工卡 30 分钟消磁**：不实现无感续期（refresh 链路）的应用，30 分钟后接口集体 401。
  续期链路是每个持工卡调别人的应用**自己的责任**。
- **一次性凭证的两只老虎**：ticket 30 秒 / code 60 秒，用后即焚；前端框架的重复执行
  （StrictMode）会把同一凭证消费两次 → 401，必须前端缓存去重。
- **introspect 是逐请求加一跳**：不打缓存的高频接口每次多 5-10ms + 一次 AI Hub 调用日志
  落库。官方建议 60 秒 TTL 缓存，但缓存也意味着**吊销延迟 60 秒才生效**——吊销敏感的
  接口别缓存或缩短 TTL。
- **AI Hub 单点**：行政中心关门 → 新登录全停、互调 introspect 全停。存量本地胸牌会话在
  有效期内不受影响。这是"唯一发卡处"设计的固有代价，无解，只能接受并演练降级。
- **代理姿势（/api/v1/proxy/）有五重校验 + 路径白名单**：没配 `allowed_prefixes` 的路径
  直接 403。适合低频前端直调，不是互调的默认通道。
- **测试环境与生产环境的行政中心互不相认**：拿测试环境的工卡打生产 introspect 必 401，
  配置按环境切（本地开发 `localhost:30080` / 测试 `111.229.103.94:30080` /
  生产 `131.131.2.10:30080`）。
- **两个角色维度别混**：系统角色（admin/department_admin/employee，全局）与应用内角色
  （app_roles，"用户×应用"标签）是独立维度——普通员工可以在某个应用里被授予应用管理员。
  空标签 = 当普通用户。
- **权限白名单变更不实时**（方式二/三/四路径）：`required_permissions`、app_roles 在
  登录/发号时校验或刷新，用户不重登则副本滞后（最长会话有效期那么久）。

## 压缩成三句话

1. **公司只有一个发卡处（AI Hub），所有凭证都出自它，应用之间从不互发凭证**——要信对方，
   打电话问发卡处（introspect，方式六）；要替整个应用办业务，刻部门章（方式五）。
2. **用户进门有四种姿势，按部署形态选**：同一 SPA 直传（一）、同域过闸机（二）、跨域
   一次性通行条（三）、独立入口授权码换卡（四）；只有方式四支持用户直接打开应用 URL。
3. **应用对内发自制胸牌（本地 JWT）管业务权限，对外来凭证一律不自己判**——原样转交
   发卡处核实，按 `caller_type`（人/章）决定给个人数据还是服务数据。
